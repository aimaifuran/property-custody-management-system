# Admin and User custody workflow

## Automatic form numbers

New IAR forms use a 3 to 4 digit number: `001`, `002`, and so on through `9999`. This sequence continues across calendar months. RIS, ICS, PAR, PTR, and PRS retain separate monthly sequences in `YYYY-MM-NNN` format, using the current month in Asia/Manila. Opening or cancelling an editor does not reserve a number. The server assigns the final number on save, so two accounts that opened the same preview receive different saved numbers.

The server keeps a persistent atomic counter and checks previously saved numbers, including deleted records, so old numbers are not reused. Historical and explicitly entered API numbers remain supported, and editing an already numbered record does not generate a new number. Forms generated by issuance, transfers, and returns use the same sequence as manually created forms. No extra numbering buttons are required.

IAR No. is editable and accepts only 3 to 4 ASCII digits, preserving leading zeros. Leaving the suggestion unchanged uses automatic allocation on save; entering another valid number saves that number and advances the same counter. Duplicate IAR numbers show a clear error and retain the form entries. Existing formatted IAR numbers remain unchanged when correcting other details. An old unsaved new-form draft receives a current numeric preview while retaining its entered items. Automatic numbering stops at `9999` rather than wrapping or issuing five digits.

Expired access tokens are refreshed using the existing valid refresh cookie, then the original API request is retried once. If the session cannot be refreshed, an unsaved IAR remains in the editor and is retained for the same account in this browser tab while signing in again. Successful saves clear that draft and display the saved record.

## Stock and requests

The user workspace has exactly two sections: Issued Items (`/my-issued-items`) and Returned Items (`/my-returns`). Request, standalone inventory, administrative forms, transfers, reports, and user management routes are restricted to the admin workspace. Direct user visits to RIS and its request aliases redirect to Issued Items. Returned Items is available from the sidebar; the Issued Items page does not contain an extra View Returned Items action. A denied permission displays an explanation without redirect loops.

Admins receive stock through IAR, selecting Consumable Supply or Asset and recording quantity, unit cost, and optional property/serial numbers. Receipt saves IAR, inventory, stock balances, ledger entries, Property Card and the existing RIS draft in one MongoDB transaction. Posted stock numbers, quantities, costs and types cannot be edited into a different receipt. Additional stock uses a new IAR.

Existing catalog items retain Asset as the compatibility default. Admins classify items directly in the existing IAR item rows. Classification changes apply to future issues and are blocked while the stock has active asset accountability. Historical documents remain intact.

Admins record mixed supply/asset RIS requests for user accounts in the existing `/ris` form and review, reject, or approve and issue them there. Users see the recorded status and issued items in their account. Consumable supplies deduct stock through RIS without ICS/PAR. Assets continue to use the existing unit-cost rule: below PHP 50,000 generates ICS; PHP 50,000 or above generates PAR. Classification uses unit cost, not the total value of the requested quantity.

## Acceptance and transfer

ICS/PAR forms are available in the admin workspace; users see their document references in Issued Items. The custody acceptance API remains available and records the user ID and timestamp, updates the form receipt date, and records an acceptance hash and activity entry. It is a click acceptance record; it does not capture a handwritten signature image.

The existing `/transfers` form handles sender requests, receiver confirmation, and admin decisions. Only the current custodian can request a PTR for an accepted asset. The receiver confirms physical receipt, then an admin previews and approves the transfer. Pending transfers leave accountability with the sender. Approval reassigns the active accountability and creates a new ICS/PAR for the receiver's remaining quantity, preserving original forms and transfer history. Rejection releases the asset's movement lock and retains the sender's accountability. Annual office reports use approved transfers for the custodian at the selected year end and avoid counting linked forms twice.

## Returns

Users submit returns through the existing Returned Items screen. Current accountability records supply asset details, including transferred assets; consumables retain their original RIS references. A pending return retains accountability and does not increase stock. A property can have only one pending transfer or return.

Admins inspect the physical item and choose Serviceable or Unserviceable for each line before confirming receipt in the existing `/returns` form. Confirmation updates accountability, inventory status, Property Card, serviceable stock, and Returned Supply records together. Partial returns retain the remaining accountability. Full returns remove the asset from the active custodian list. Serviceable quantities return to available stock; unserviceable quantities are recorded for disposal and do not increase available stock. Repeat confirmation cannot post stock twice. Rejecting a return retains accountability and releases the movement lock.

Returned To name, designation, and date are editable during receipt confirmation. Empty pending fields initially show the receiving admin's details. Admins can also correct this signatory on completed slips using the existing Update PRS action. Corrections synchronize PRS and Returned Supply in a transaction without posting stock again. Item quantities, conditions, and the original custodian remain locked on completed workflow returns.

New standalone Returned Supply entries linked to an issued RIS are received through the same transaction and create a linked PRS. Unlinked historical forms remain document records; they cannot alter inventory without an exact issued-item reference. Received movement quantities and conditions are locked; document notes and receiving signatories remain editable. Existing historical returns are not automatically reposted into stock.

## Notifications and access

Workflow notifications are recorded on the server. User return confirmations and rejections link to Returned Items. Users see their own requests, issued items, and return history. Administrative catalog, receipt, transfer and approval screens remain admin-only.

## Database and verification

MongoDB must be a replica set or Atlas connection. New optional schema fields require no database reset; provision Mongoose indexes if automatic index creation is disabled. Existing records are preserved. No deployment or production data migration is part of these source changes.

From the repository root:

```powershell
node --test backend/tests/*.test.js
```

From `frontend`:

```powershell
npm.cmd run build
node --test tests/*.test.mjs
node tests/responsive.browser.mjs
```

The custody integration test covers mixed supply/asset issuance, receipt rollback, access restrictions, form acceptance, receiver confirmation, transfer approval and rejection, partial/full returns, unserviceable returns, repeated actions, and return-posting rollback.

Simple tables stack into labeled rows when their available width is small. Official layouts that require wide columns scroll within the table region. Form fields, saved records, and actions adapt to workspace width. The isolated browser audit checks both roles at 320, 375, 768, 1024, and 1440px without changing real accounts or data.
